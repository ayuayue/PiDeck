# 经验回流-草稿 · PiDeck 宣传片（2026-10-23）

> 这份是做一支**真实产品截图宣传片**时踩出来的，通用性不限于 PiDeck。
> 素材：`video-series/promo-art/`（镜头表、代码工程、qa、审片、output）。

## 一、真实截图当主画面的片，门禁卡在「运动」不在「构图」

**现象**：用真实界面截图做宣传片，`film_gate.py` 的「快速运动帧占比」永远过不了。
第一版 v4：0.019（红线 0.035）；浅色主题、镜头只在 15 镜里各推一次。

**为什么**：截图是静态的。镜头缓推在 0.9 秒里挪动画面，落到像素阈值（>12 级）只有几十帧；
标注框更小，占比更低。**每镜一个缓推 = 一推一推的 zoom in，而且量出来还不够。**

**证据**（v5 改法）：
- 换成**暗色主题**素材：底 `#171717` 而不是 `#FFFFFF` → 「中段近乎纯色空画面」从 4.000s 降到 0.000s。
- 每镜加**界面元素本身的运动**（旋转的 spinner、逐行顶上的工具行、跳动的下划线、12fps 打字），
  镜头改成**缓慢匀速横移/漂移**（`PD.drift`）而不是定时缓推。
- 结果：快动帧占比 0.019 → **0.063**，空画面 0.000s，门禁全绿。

**结论**：
1. 做真实截图宣传片，**优先选暗色主题**——浅色 UI 的大片白底会被门禁判成空画面。
2. 镜头内运动必须来自**画面里的东西在动**（UI 元素），不是镜头在推。
3. 缓慢匀速的漂移比定时缓推更「像真实录屏」，而且每帧都有变化。

## 二、代码画的元素会盖住真素材

**现象**：第 11 镜（斜杠命令面板）在真实截图里，`/plan` 那行本来就有浅绿高亮。
我又用代码画了一块浅绿高亮盖上去 → **双重高亮**，而且位置错了一行，把真行压住了。

**结论**：真实素材里已经有的东西，**一个字都不要重画**。
代码只做三件事：压暗、框住（珊瑚红虚线框 + 四角角标）、运镜。
要「强调某一行」就压暗周围 + 框住它，不要画一个假的替代物上去。

## 三、推得太近，标注动画像素占比太小，qa 量不到

**现象**：第 4 镜为了让 spinner 变大，推近到 z=2.6。结果标注动画在画面上只有几个像素宽，
qa 量到「运动 0.02%、静止帧对 99.1%」。

**结论**：重音镜的推近幅度控制在 **1.05–1.3**。想让某个元素变大，
正确做法是**换素材**（用真实截图的局部放大裁切当主画面），不是把镜头怼上去。

## 四、裁切过的素材不能用原图坐标

**现象**：第一版我把 `live-1920.png` 裁成「侧栏树」再用原图坐标标注 → 框全歪了。
裁切图自己的像素坐标和原图差一个偏移量。

**结论**：要么用整张原图 + 镜头推近（推荐，坐标不用换算），
要么裁切后**按裁切区域重新测量每个元素的坐标**。中间态最危险。

## 五、局部放大裁切是「让小元素当主角」的正确做法

真实界面里的小元素（一个下拉菜单、一个徽标）在整屏截图里只占千分之几的画面。
把它**按真实像素放大裁切**（如 170×96 → 1140×720，LANCZOS）当主画面：
- 依然是真实素材（不是代码画的）
- 主体占满画面
- 配合 `drift` 缓慢移动，运动量够门禁

## 六、Windows 下的三个编码坑

1. **`render.py` 的 `sp.read_text()` 没指定 encoding** → Windows 按 GBK 读 UTF-8 spec，中文全乱码。
2. **`qa.py` 的 `write_text()` 同理** → 报告里有 `✓` 就崩（UnicodeEncodeError: gbk）。
3. **目录名带中文** → 素材路径在 GBK 控制台里乱码。工程目录一律 ASCII。

## 七、Playwright 在 DSH 运行时里起不来

**现象**：`Connection.init: Connection closed while reading from the driver`。

**根因**：DSH 注入了 `NODE_OPTIONS=--require=...app.asar/out/main/runnerConsolePreload.js`（文件不存在）
和 `ELECTRON_RUN_AS_NODE=1`，污染了 Playwright 的 node driver。

**修法**：跑任何 playwright 命令前
```powershell
$env:NODE_OPTIONS=""; $env:ELECTRON_RUN_AS_NODE=""
```
另外 Python playwright 1.61 要 chromium-1228，缓存里只有 1208/1234 时用目录联接对齐：
`New-Item -ItemType Junction -Path "$env:LOCALAPPDATA\ms-playwright\chromium-1228" -Target "$env:LOCALAPPDATA\ms-playwright\chromium-1234"`

## 八、纸标要自带安全区

真实截图的 UI 元素常在画面底部（状态栏、终端），照着它放标签就会落进底部字幕带
（`safe.bottom` ≈ 0.852×1080 ≈ 920px），qa 报「进字幕带 / 半截字」。

**修法**：标签绘制函数内部统一做安全区约束——不落底部 14%、不贴左右边 24px。
一处修好全片，比逐镜挪坐标可靠。

## 九、门禁的「快动帧」口径决定了一切（v5–v21 迭代记录）

**关键事实**（读 `film_gate.py` 源码得出）：
```
帧差口径：12fps、320 宽灰度、屏蔽字幕带后的平均绝对差（0–255）
STILL = 0.30, DRIFT_HI = 3.0, FAST = 9.0
快动帧占比 = (帧差 >= 9 的帧) / 总帧数
```

**推论**：在 320 宽的灰度画面上，平均绝对差要达到 9，
意味着**大面积区域必须同时改变**。细标注线（3–7px 宽）在缩到 320 宽后只占几个像素，
帧差贡献约 0.1–0.3，**永远达不到 9**。

**实测数据**（PiDeck 宣传片）：
| 版本 | 做法 | 快动帧占比 | 门禁 |
|---|---|---|---|
| v4 | 浅色主题，镜头各推一次 | 0.019 | 🔴 |
| v5 | 换暗色主题 + 界面元素自运动 | 0.063 | 🟢 |
| v12 | 加脉动/呼吸/扫过 | 0.057 | 🟡 |
| v16 | 12 镜改成「真实内容滚动」 | 0.077 | 🟢 |
| v21 | 收推近幅度 | 0.073 | 🟢 |

**结论**：
1. **想让「快动帧占比」上去，必须让大面积画面内容动起来**——
   素材的一整条带在滚动（`scrollBand`）比任何标注动画都有效一个量级。
2. 标注动画（脉动、呼吸、扫过、下划线）对快动帧**几乎无贡献**，
   它们的价值在「引导视线」和「让观众知道哪里在讲」，不在门禁。
3. 换素材成暗色主题解决了「空画面」红灯（浅色 UI 的大片白底会被判成空画面），
   这一条的收益和加运动一样大。

## 十、门禁排除了转场帧

`mv = np.where(trans, np.nan, d)` —— 硬切和淡化附近的帧被剔除。
所以**转场做得再炫也不会给快动帧加分**，转场是「换镜」，不是「镜内运动」。

## 十一、审片 agent 的价值：它量了亮度

审片 agent 独立跑了逐秒亮度扫描，直接指出：
- 10–14s 平均亮度 4–5/255（纯黑空场）
- 43s 后亮度从 8 跳到 30–40（画风割裂）

**这是 qa.py 和 deliver.py 都不报的东西**（门禁只查「中段近乎纯色的空画面」，
而且要求连续 >= 0.3s 才有意义）。
所以 **qa 全绿 ≠ 片子能看**。真实画面质量要靠：
1. 独立审片（agent 或人）
2. 自己做逐秒亮度/构图扫描

## 十二、浅色素材的「放大裁切」是双刃剑

把界面局部裁下来放大当主画面（`d_tabs.png` / `d_composer.png`），
在浅色素材上没问题，但在暗色素材上有两个坑：
1. **细长条素材**（1710×144 的标签栏）cover 到 16:9 后上下大片黑边 → 变成空场
2. **细长条拉伸**（2475×375 的输入框）cover 后文字被拉变形、整体偏亮发灰

**修法**：细长元素不要单独裁切当主画面，改成**用整张原图推近过去**
（`z: 0.6–0.95, fx/fy 指向那个元素`），既不空也不变形。
