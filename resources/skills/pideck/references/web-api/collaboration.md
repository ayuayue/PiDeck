## 5.6 与另一个会话按 PR 模式协作

**必须抢活来干：看到缺陷就动手，不等分配、不等对方先改、不问「要不要我做」。** 发现的那一刻就是开工时刻，判断与动手之间不留缓冲。

三条落法：

1. **发现即改**。你发现的问题归你改，不写在回执里让对方改。对方发现的也归对方改——抢的是「我发现的我干」，不是抢别人的发现。
2. **能当场验就当场验**。不把「可能是这样」交给下一轮去证；两分钟能造样本的事，写「也许」就是推。
3. **不留口子**。「下一轮再说」「你判、你改」「我不会改所以提出来」——这三句都是同一个动作：把手上的活换了个说法交出去。

判据：`~/.pi/agent/bin/check-round-robin.mjs` 要求**发现者与修改者是同一会话**，`已改` 写了发现问题却是空 = 红。**只有两类例外**：

**例外一：不可逆且无退路**（删仓、强推、合并到别人的分支）——先快照，再问。

**例外二：凭据不在你手上**（无写权限、无令牌、目标仓是别人的）。这类动作由持凭据的人执行，你写清命令原文与期望返回，**并且自己先跑一次把原始返回贴出来**——跑过才知道是「缺这一项权限」还是「token 全废」，这两个的后续动作完全不同（2026-11-17 实测：`GET` 成功、`PATCH` 403、**上游仓**的 `permissions` 是 `pull:true push:false`，是缺 PR 写权限不是 token 废。**注意那是当时那枚 token；换一枚有 PR 写的 token 后同一份数据变成 `PATCH` 200 而合并仍 403，两件事都在下面的表里**）。没跑就写「无凭据」，那还是推。**跑通了（200）说明你有权限，那就不属于例外——自己做。**


**「无凭据」要写清缺的是哪一项。** 写「403」不够——持凭据的人不知道该改 token 的哪个开关。写「缺 `Pull requests: Write`，且 Repository access 未含上游仓 `<owner>/<repo>`」，对方才能一次改对。2026-11-17 实测：三个 token 连续 403，每个都只返回 `Resource not accessible by personal access token`，一次都没说缺什么；拿它分不清「缺这一项」与「token 全废」，只能一个个试。判据是读那条 `GET` 通不通：`GET /user` 200 而 `PATCH` 403，就是缺这一项，不是 token 坏。

**「写权限」在 GitHub 上是三种能力，不是一种，而且它们分属两个仓。** 2026-11-17 实测同一时刻：上游 `ayuayue/PiDeck` 是 `pull:true push:false`，同一个 PR 的 head fork `op15066212/PiDeck` 是 `admin:true push:true`。同一份 PR 上 `PATCH /pulls/570` 返回 200（正文改得动）、`PUT /pulls/570/merge` 会 403——两件事发生在两处仓上，混成一句「403」分不清缺哪一种，后续动作完全不同：

| 能力 | 判据 | 缺了会怎样 |
| --- | --- | --- |
| 读 | `gh api repos/<o>/<r> --jq .permissions` 给 `pull:true` | 连 PR 都看不到 |
| PR 写 | `PATCH repos/<o>/<r>/pulls/<n> -f body=…` 返回 200 | 改不了标题与正文，但能评论 |
| 仓库写 | 同上 `permissions.push` 为 `true` | 推不了分支、合不了 PR——合并按钮按下去 403 |

所以「能改 PR 正文」和「能合并」是两件事，**推分支是第三件**：推看 head fork，合并看上游。写「无凭据」时要说清是这三项里的哪一项、**是哪一处仓的**，并贴上那处仓 `permissions` 的五个字段作为现取证据。
**两个人同时发现同一个缺陷时，动手前先说一句。** 发一条「我在改 `<文件>`」，对方在改就停手等它交。抢活抢的是「我发现的我干」，不是「同一行两个人一起写」——R15 活样本：两个人同时改 `src/lex.ts`，改动混在同一个工作区，直到测试红了才分清谁改了哪一段。

**交付之前先假定：对方手上只有这一条消息。** 它可能没读过这个技能、没打开过仓、看不到你的屏幕。所以交付里要自带四件——对象（绝对路径）、版本身份（md5 与字节，现取）、判据命令与它的 rc、算完成的标志。写「见附件」「如上」「同前」，对方就得先问你；问一轮的时间够贴全三遍。

**改完必须当场交对方，不发消息等于没改完。** 落盘后立刻发一条消息：对象与 md5、改了什么、跑过哪些判据与 rc、坏样本在哪。PR 评论不算交付、签核文件也不算——对方不会去翻你的 PR，也不看你目录里的 signoff。写得再详细，没人读就是零。

**签核第一屏写六行**：`轮次: Rn`、`提出者: <会话名>`、`发现者: <会话名>`、`修改者: <会话名>`、`复核者: <会话名>`、`交付: <发给对方的时刻>`。再加三段：`审查:`（读到什么、发现什么）、`已改:`（真改了什么）、`未改:`（原因按下一段的判据写）。

`~/.pi/agent/bin/check-round-robin.mjs` 判四件事：发现者与修改者同一会话、修改者与复核者不同、`交付` 行在、`未改` 要么写「无」，要么写三种客观原因之一（无写权限 / 无凭据 / 文件不在本机），另一律红。再加推责词表（11 个）。缺任一字段也红。口径上限：它只扫「已改」「未改」两行的值，不扫全文——全文里引用规则原文会误伤（「不许写下一轮再说」这句自己就含禁用词）。所以**消息正文里的推责说法 rc 抓不到，只能由收到的一方当场指出**。


**交接用文件，不用消息正文。** 中文经命令行参数会被代码页转码（5.1 末尾有实测），提案超过几十行也会被截断。约定：提案写 `proposals-rN.md`、回执写 `review-rN.md`，发消息只发路径与第一行署名。

**每条消息第一行必须署名，md5、字节、行数、时间四样缺一样，对端只能猜。**

```
[<发送者> → <收件人> · <对象> <md5前8位> · <字节>B · <行数>L · <时间>]
```

命令：`md5sum f | cut -c1-8`、`stat -c %s f`、`wc -l < f`。数字一律现取（理由见 9.1）：2026-11-17 白争一轮，一方写「634 行」、另一方核到 638，两个人盘上的文件本来就是同一个。接收方第一步拿这一行的 md5 与自己盘上的比，不一致就回「你这条基于旧版」。

**证明对方真读了原文**：给它关键词，让它回贴包含该关键词的**整行原文**，你拿盘上那份逐字对。

```
1  含「子非鱼」的那一行
2  含「别拿错变量」的那一行
```

行号不作证据——插入一行就漂。关键词散在全文不同区段，能一次贴准的只有真读过：2026-11-17 用五个关键词（71 / 104 / 289 / 529 行）验过一轮，逐字一致。只说「我看了」，与没看无法区分；贴得出五行，才叫读过。

**每轮产出必须是 git commit，不能只改盘上文件。** 判据：`git log --oneline -1` 能指到这次改动。在分支上改、一次提交一件事、提交信息写为什么；`SKILL.md` 这种装在多处的文件，先 commit 再同步副本，回执里同时给 commit 号、`git diff --stat`、各处 md5 与判据 rc。桌面临时复制与副本同步是部署动作，不算改动凭证。

**动手前看，交回执时写。** 动手前跑 `git log --oneline -3` 与 `git status`：对方最近落过你要改的那一节，就先停手合并。核的人在回执里必须写一句「这次改动有没有第二处说同一件事」——语义重复脚本抓不住，2026-11-16 实测同一件事被写了三段，四个判据全绿。

**凭据在谁手上，就由谁执行那一行命令。** 发现方给命令原文，持凭据方原样执行、回贴命令与输出。对外推送不可逆，许可只能来自用户——核的人不能代用户说「可以推了」。别人的仓只 pull 与建 PR，合并是仓主的事：**上游仓**的 `permissions.push:false` 就不要试 merge（实测返回 404 不是 403，容易被误读成「PR 不存在」）。**推分支不看上游，看 PR 的 head fork**——fork 上你多半是 admin（2026-11-17 实测 fork 是 `admin:true push:true`；同一句话写成「我们没有 push 权限」写进了十几轮回执，26 个 commit 因此躺在本地没推）。

**缺权限时两个码不同，别混**：merge 返回 404，改 PR 正文返回 **403**（2026-11-17 实测：`gh api -X PATCH .../pulls/N -F body=@f` → `Resource not accessible by personal access token`）。两种都不该读成「PR 不存在」。区分「token 失效」与「缺这一项权限」的办法是先 GET 同一个资源：GET 成、**上游仓**的 `permissions` 显示 `pull:true push:false`，就是能读不能写（这是合并与改别人仓的门槛，不是推自己 fork 的门槛）。

## 9.1 每句话带来源

**判据只有一条：这句话会不会被别人当成事实引用。会，就必须能追到「谁说的、依据哪一版」；不会，署名只是噪声。**

| 去哪 | 署名形式 | 缺了会怎样 |
| --- | --- | --- |
| 发到另一个会话 | 第一行署名，格式见 5.6 | 对端没有可比的东西，只能猜你基于哪一版 |
| 回给用户 | 每条断言标来源：`我跑过` / 对端报的 / `未验证` | 用户分不清「你核的」与「别人说的」 |
| 写进盘上（文件、commit、PR 正文、签核） | 依据版本加时间；正文写「依据 `<md5>`」 | 半年后的人不知道这句话当时基于哪一版 |


**同步的清单用 `find` 出，不手写。** 手写清单一定漏：2026-11-17 同步一份判据脚本，手写四条、扫出来九条，漏的三处里有一处是用户实际加载的那份——它红着，用户看到的判据就是旧的。判法：`find ~ -name <文件> -not -path "*/node_modules/*" | while read f; do md5sum "$f"; done | sort | uniq -c` 输出只有一行才算同步完。写成「七处已同步」而没贴这条输出的，按未同步算。

**但 `find` 不跟 junction/symlink，这一条比手写漏更隐蔽。** 2026-11-17 同一个问题：find 数出五处，实际七处——`~/.agents/skills` 与 AppData 下几处都是指向 magpie 库的链接，find 看不见它们，而少算的方向正好是「以为同步完了，实际还有一份」。手写漏是因为想不全，靠纪律补；find 漏是因为工具默认不跟链接，纪律补不上。**判据是两条路的并集**：先把已知候选逐个 md5sum 一遍，再用 find 扫一遍，两边差出来的就是链接位置。只贴一条路的输出的，按未同步算。

**同一个道理有时间维度的版本：查「这份文件曾经有没有 X」，要取全部相关 commit，不能只取 HEAD 或第一版。** 2026-11-17 实测：一个人说「R27 那份回执有两个签核块」，另一个人查了初版提交，计数是 1，回「与你不符」。真相是重复出现在中间那版（重排时插了新的没删旧的），修复在第三版。三个版本里只有中间那版有问题，只查第一个就得到假结论。命令：`git log --oneline -- <文件>` 列出全部，再 `git show <每个>:<文件> | grep -c '^字段:'` 逐个比。


**两个人先后动同一个仓，比同一时刻的现值，不是各自报过的值。** 比较时同一秒内现取两次；隔了提交的差值写成「你的时刻与我的时刻之间发生了什么」，不是「你说的与盘上不符」。


**同一个判据在不同时刻跑出的数，只在采样条件相同时才可比。** rc 是二值，不受影响；耗时、条数、字节这类量会随并发与负载漂——2026-11-17 实测同一条 `npm run check`，同时在跑别的 node 进程时 5327 ms，单独跑 2118 ms。报耗时要么带上采样条件（同时还在跑什么），要么不报。别把两个时刻的差读成「判据变快」或「判据退化」。
**三个人称分清：我、你、他，各自指谁要在同一句里落地。** 我＝署名行的发送者；你＝收件人；他＝用户、别的会话、仓主三者之一，每处写明哪一个。别写「我们这边」「对方」这类不指名的说法——收件人不止一个，指代会漂。

**转述要标明出处。** 对端报的数字写进自己的回执时前面写「对端报的」；不标等于冒充自己核过。

**核对交付物，用交付物本身的字节，不用描述它的那句话。** 2026-11-17 实测：连续十几轮回执都写着「PR 第 62 行的 md5 已更新」，没有一次跑过远端取字节——那 62 行是 PR 的说明文字，技能本体落后 26 个 commit，两个人一起没发现，因为把「回执里写了」当成了验证过。判据只有一条，与本地比对：

```bash
gh api repos/<head.repo>/contents/<path>?ref=<head.sha> --jq .content | base64 -d | md5sum
```

**这条要整条跑，别拆成两步。** `B=$(gh api ... | base64 -d)` 会吃掉末尾换行，`printf "%s" "$B"` 不补回来，于是稳定少 1 字节——差 1 字节看起来像「不一致」，实际是量它的工具改了它。`echo "$B"` 侥幸对（它会补一个换行），所以同一个错法两种写法给出两种结论。2026-11-17 实测：五个文件里两个按拆两步的写法判 DIFF，改直管道重跑全 SAME。
回执里写「已交付」而没贴这条输出的，按未交付算。

**这三句不算署名**：「实测」「已验证」「我看了」——不写命令、文件名、md5，与没说是同一件事。

## 9.2 说人话

**开口之前先做一次假设，不是写完再查：读者什么都不知道、只看第一屏、不记前情、不关心你试错几次。**

这一条是所有写字的起点，不是清单最后一项。落笔那刻就按最差读者写：他要事先知道的东西当场给；他不认识的名字当场解释；他看不到的「刚才」，把原话重述一遍。写完再回头补，补出来的仍是作者视角。

**动词要有画面。** 抽象名词换成手能做的动作，读完第一屏要能说出「谁对什么做了什么」。不止修 bug——同步、验证、回滚、提交、删除，凡是名词化的说法都换。

| 别写 | 说成 |
| --- | --- |
| 修复了这个缺陷 | 砍了一刀 |
| 重构了模块 | 推倒重写 |
| 优化了性能 | 让它快了一截 |
| 部署完成 | 装到机器上了 |
| 同步了两边 | 对了一遍表 |
| 验证通过 | 跑了一遍，没红 |
| 回滚了改动 | 退回去 |
| 提交了 | 落了一笔 |
| 撤销了那次改动 | 拿掉了 |

**同类一次砍完。**「砍一刀」是一刀把同类全砍掉，不是挨个修。

**对另一个会话说话，也是说话。** 它不记得上一轮、上下文随时被压缩、可能刚重启。跨会话消息与任务书一律自包含四件：要它做什么（一句）；依据（绝对路径、md5、字节）；算完成的标志；它可以拒绝的方式。不用「上一条」「刚才那个」指代前情。

**离开本文件的文字按 0.4 写。** 提案与回执这类长文件仍走文件路径；规则原文抄进消息，不写「按 5.6 办」。

## 9.3 一切改动都进 git

**判据只有一条：`git log` 能指到这笔改动，工作区干净。**

1. 改完立刻提交，不攒。攒着的改动会被下一次改动污染。
2. 提交信息写为什么，不写「update」「fix」。
3. 有远端就推，推完用 `git ls-remote <remote> refs/heads/<branch>` 与本地 `git rev-parse HEAD` 比对——不看自己的输出，`git push` 之后跟着别的命令时 rc 会是别人的。
4. 动手前跑 `git status`：有别人的脏文件就先停，别把两件事混进一笔。

**行数不是判据。** 判「追加还是替换」要看 diff 里的 `-` 行：把一段删掉再添一段，行数可以一模一样。判据：`git diff --numstat <旧> <新> -- <文件> | awk '{a+=$1; d+=$2} END{printf "%d %d\n", a+0, d+0}'`，加 > 0 且减 = 0 才是纯追加，「0 0」是没有行增删（改名也会得 0 0）。三个坑：`grep -c "^-"` 被 `--- a/file` 表头喂成恒 1；两版相同时 `--numstat` 一行都不打；只聚第二列分不出纯追加与无改动。

**例外只有两条**：会变的值（令牌、时间戳、机器相关路径）不进仓；大二进制不进仓，留个生成脚本。

```bash
git status --porcelain | wc -l   # 期望 0
git log --oneline -1             # 能指到这次改动
```

坏样本：改一个文件不提交，第一条就不是 0；用 `git status --porcelain | head` 会拿到 0，那是 head 的退出码。

**加判据之前先答一问：这个形态会自然出现在谁的回执里。** 答不出来就别写判据，把它记进口径上限。2026-11-17 实测：一晚加了 29 条坏样本，全是为「刻意构造的绕法」——全角引号包裹字段、字段名里插零宽字符、表格里嵌列表。真实回执里出现过的事故只有一种（同一份签核两个「未改」），第一条判据就抓住了。剩下的都在防没人会写的形态，而改动本身把判据文件插坏四次（两个人各两次），靠从 git 恢复整份才救回来。

三个停止信号，出现任意两个就停：

- **改坏的次数超过抓住的次数。** 加判据的过程中插坏文件 4 次、抓到自然事故 4 次，打平；再往下就是净亏。
- **构造的形态答不出「会出现在谁的回执里」。** 零宽字符有真实来源（从网页或 PDF 复制模板会带不可见字符，字段名静默失配，判据恒假绿）——该修。全角引号包裹没有来源——记进上限。
- **PR 的 diff 比缺陷大。** 5 文件 +479 −263 只为拦一个两次重复写字段的笔误，继续加会让人宁可不合。

反过来说：真实来源那一条要修到底。判别的唯一标准是「会不会有人在正常做事时撞上它」，不是「我能不能构造出来」。

**技能的每一行是给人读的，判据的每一行是给机器跑的，所以出错代价不同。** 2026-11-17 实测：一晚插坏文件 4 次，全部在判据里（两次重复声明常量、一次裸反引号断了字符串、一次把语句截掉半行），技能正文 0 次——多一行规则只多一次误读机会，多一行代码多一次插坏机会。所以「说不出谁撞的、撞了几次就不写」这条对判据要更严，对规则可以略宽。

**整份文件改写要用不截断的读法。** 2026-11-17 实测两次：用编辑器工具读一份 688 行的技能，它返回的是片段（有截断提示但容易被忽略），把片段写回去等于删掉没读到的部分——一次丢了 101 行，工具不报错，只是文件变短了。正确做法是 `node -e "require('fs').readFileSync(p,'utf8')"` 或 `cat`，或者在写回之前对一次字节数：`stat -c %s` 改前改后相等或只差自己改动的那几个字符。判据：写入后用 `wc -l` 与 `wc -c` 对一次，行数少了就是被截断过。

**移动已写好的字段块，同一个 commit 里要删原处。** 2026-11-17 实测三次：把签核六行复制到文首（为了让它在 `check-round-robin` 读的前 1200 字符内），原来的块留在正文里没删，于是同一份文件出现两个「发现者」「交付」「未改」。check-self-contained 里那个 dupFields 抓到的四次自然事故里有三次是这个动作造成的，都是同一个人的同一手法。判据命令：`grep -c '^发现者:' <文件>` 必须等于 1，五个字段各查一遍。

## 9.4 每来一件新事，先重排

**新任务进来时按顺序做三件：列全、排序、只做队首。**

1. **列全**：所有未完成项，一项一行。漏掉的一项会变成之后某次返工。
2. **排序**：晚一周的损失 ÷ 工期。分子指不出具体会话、具体文件的就是 0；分子为 0 的事不做，并说清为什么不做。
3. **只做队首**：做完再排一次。半途插队，两件都脏。

判据：能说出现在做哪一件、为什么它在最前、其余各在第几。

**用户的话优先于另一个会话的话。** 对端回执进来时，先看用户有没有没处理的指令：有就先做用户的。对端可以等，用户的指令等成「未完成项」就是错序。

**别人的东西不进队列。** 有上游维护的仓、别人的技能、别人的 PR——没经用户明确批准，一律不碰、不报、不列进待办。判据：待办清单里出现不属于自己的仓或文件就红，一条也算。
