# 与另一个会话协作

主干讲了怎么发消息、怎么等它干完。这里讲怎么一起改一件东西而不互相踩。

## 四个角色，人的那个不在轮换里

提出者是用户：他提要求、定验收、随时插入新事项。发现、修改、复核是三个 agent 角色，按轮次算术轮换。

| 角色 | 谁 | 必须做什么 | 不许做什么 |
| --- | --- | --- | --- |
| 提出者 | 用户 | 提要求、定验收标准、决定做不做 | 不进署名，不算进轮换 |
| 发现者 | 上一轮的复核者 | 指出缺陷：贴原文、贴判据、给一条能返回真假的命令 | 让本轮修改者替自己找判据 |
| 修改者 | 轮次算式定出的那一方 | 落盘改完，贴改后原文与 rc | 只提不改；写「待你改」 |
| 复核者 | 另一方 | 读原文、跑判据、造坏样本，回 accept 或 reject 附 md5 与 rc | 替修改者改；只回「认可」 |

**发现者由结构决定，不由谁先说。** 发现者就是上一轮的复核者——它核的时候看到的缺陷，下一轮由它自己改，中间不经转述。当轮不是上一轮复核者的一方，不能声称自己是发现者。这一条替代旧的「谁发现谁改」：那个判据要每轮自证「我先发现的」，而自证不可观测。2026-11-17 实测，连续五轮双方都写「发现者：对端、修改者：对端（待你改）」，实际每一次都是自己找到的问题。

**角色按轮次算术换，不按自述换。** 轮次记作 Rn：修改者 =「n 为奇数则甲、偶数则乙」的那一方，复核者是另一方，发现者是上一轮的复核者。R1 甲改乙核，R2 乙改甲核，R3 甲改乙核。连续两轮同一个人当修改者，就是没换边。

**签核第一屏写三行**：`轮次: Rn`、`修改者: <会话名>`、`复核者: <会话名>`。原先有一个脚本按 `轮次` 排序、看 `修改者` 是否严格交替；那个脚本（`check-round-robin.mjs`）随技能拆成多文件时被移出本技能，**所以这条现在只有人工判据**——交替靠人看，别把「我没看见连续两轮同一人」当成验过了。

**没有「待你改」这个状态。** 署名行里的修改者必须是已经落盘改完的那一方。写成「修改者：对方（待你改）」就是把活推出去。2026-11-17 实测：连续五轮这么写，每轮都说不出「对方机器无写权限」或「文件只在我这盘上」两条中的任何一条——同机、有写权限、能提交，两条都不成立。

## 两条规则冲突时按这条断

**凭据在谁手上由谁执行，但改后原文必须由发现者写，执行方只许原样执行。** 别拿「先做，不满意再退」当替代——文件的改动可逆，**独立判断不可逆**：执行方一给出自己的改法，发现者读到的东西就从「问题」变成「答案」，只能顺着说同意或不同意，给不出自己的版本了。这一步做反了，退回重做也补不回来。

**判据写进签核，两条都要**：`改法作者` 与 `执行者` 是不同的人；`git diff` 里每一处 `+` 行都能指到发现者给的原文，多出一个它没写过的字，就是执行方在改措辞。缺一条按未签计。两个方向相反的实例：2026-11-17 对端列出 5 处缺陷并明写「第 4 条要用户定」，我方把 5 处全自己改了并推送，退回时发现者已被措辞污染；同一天反方向，我方连续五轮只提不改，把发现推给对方。

## 交接用文件，不用消息正文

中文经过命令行参数会被代码页转码（主干 3.1 末尾有实测），提案超过几十行也会被截断。约定：提案写到临时目录的 `proposals-rN.md`，回执写 `review-rN.md`；**发消息只发路径与第一行署名，不贴正文**。

```bash
TMP="${TMPDIR:-${TEMP:-/tmp}}"
md5sum "$TMP/proposals-r1.md" | cut -c1-8; stat -c %s "$TMP/proposals-r1.md"
[ -f "$TMP/proposals-r1.md" ] || echo "文件不在 $TMP：Windows 上 bash 的 /tmp 与 %TEMP% 不是同一个位置"
```

## 每条消息第一行必须署名

md5、字节、行数、时间四样缺一样，对端只能猜。格式固定成一行：

```text
[<发送者> → <收件人> · <对象> <md5前8位> · <字节>B · <行数>L · <时间>]
```

命令：`md5sum f | cut -c1-8`、`stat -c %s f`、`wc -l < f`。收件人填会话名或会话 id，同一次协作内保持一种，换种就注明。

接收方第一步拿这一行的 md5 与自己盘上的比：不一致就回「你这条基于旧版，我盘上是 <自己的 md5>」，不要先去猜内容差在哪。正文里再出现的任何 md5、字节、行数都必须与第一行相同；对不上就是没署。一条消息谈两个以上文件时，第一行署名给主对象，其余文件在正文里各自写 `md5 / 字节 / 行` 三连并注明是哪一个——把两个文件的数字混成一组，同样算没署。

2026-11-17 实测白争一轮：我方消息写「技能 634 行」，对端核到 638，双方为「文件是哪一个」核了一整轮——真实值 `wc -l` = 638，两个人盘上的文件本来就是同一个，错的只是消息里那个凭记忆写的数字。

## 证明对方真读了原文的办法

让它在回执里贴出原文片段。行号只作定位、不当证据——插入一行行号就漂，2026-11-16 双方各错过两次（说 186 实际 188、说 3393 字节实际 5467）。行号与片段冲突时，以片段为准。只说「我看了」，与没看无法区分。

## 每轮产出必须是 git commit

没有 commit 的改动没有历史：下一轮的人只看得到当前状态，看不到改了什么、也说不清谁改的。判断办法只有一条——`git log --oneline -1` 能指到这次改动。

做法：在分支上改，不直接动默认分支；一次提交一件事，提交信息写清为什么；`SKILL.md` 这种装在多处的文件，先 commit、再同步副本，回执里同时给 commit 号、`git diff --stat`、各处 md5 与判据 rc；PR 正文跟着提交一起变（提交表、统计数字、判据 rc 三样都要对得上）。桌面临时复制与副本同步是部署动作，不算改动凭证。

## 动手前看，交回执时写

动手前跑 `git log --oneline -3` 与 `git status`：对方最近落过你要改的那一节，就先停手合并，别各写各的。核的人在回执里必须写一句「这次改动有没有第二处说同一件事」；写不出这句，算没核完——语义重复脚本抓不住，2026-11-16 实测同一件事被写了三段，四个判据全绿。

**合并提交后，别拿「diff 为空」当等价判据。** 合并时若顺手改了内容，diff 必然非空：2026-11-16 实测合并四笔时顺手修了一处重复，`git diff <合并前> <合并后>` 是 1 处 +1 −1，而提出方报「空」。正确判据是「diff 里每一处都能指到来源」，不是「diff 为空」。

## 凭据在谁手上，就由谁执行那一行命令

只有对方能推送、能改 PR 正文时：发现方给命令原文，持凭据方原样执行，回贴命令、输出与执行时间；执行前双方各读一遍命令文本。对外推送不可逆，许可只能来自用户——核的人不能代用户说「可以推了」。别人的仓只 pull 与建 PR，合并是仓主的事：`permissions.push:false` 就不要试 merge（实测返回 404 而不是 403，容易被误读成「PR 不存在」），也不要用 `--admin` 绕过。

**写权限在 GitHub 上是三件事，分属两处仓：**

| 能力 | 判据 | 缺了会怎样 |
| --- | --- | --- |
| 读 | `gh api repos/<o>/<r> --jq .permissions` 给 `pull:true` | 连 PR 都看不到 |
| PR 写 | `PATCH repos/<o>/<r>/pulls/<n> -f body=…` 返回 200 | 改不了标题与正文，但能评论 |
| 仓库写 | 同一份 `permissions` 里 `push:true` | 推不了分支、合不了 PR |

**推分支看 head fork，合并看上游。** 两个门槛不同，混成一句「没有 push 权限」会让 commit 躺在本地不推。

**先验凭据能不能做成这件事，再排执行顺序。** 2026-11-16 实测两种失效：fine-grained token 对「本人不是协作者的公开仓」只有只读——`gh api repos/<owner>/<repo> -q .permissions` 得 `pull:true push:false`，建 PR 与改 PR 正文都返回 `Resource not accessible`；GCM 里存的是 OAuth 时，git 操作会弹 GUI 选账号，脚本里设了 `credential.interactive=false` 后 `git credential fill` 直接报 `Cannot prompt because user interactivity has been disabled`。修法（2026-11-17 实测）：

```bash
P=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
GIT_TERMINAL_PROMPT=0 git -c credential.helper= push \
  "https://x-access-token:$P@github.com/<owner>/<repo>.git" <branch>
unset P
```

两个细节都必须：`-c credential.helper=` 断开凭据管理器，否则它会把你写的 `x-access-token` 当成新账号存下，下次取凭据多一个候选、开始弹窗；`GIT_TERMINAL_PROMPT=0` 保证失败立刻返回。判据：push 前后各跑一次 `git credential-manager github list`，行数必须相同。

改 PR 正文不走 `gh pr edit`：它的 GraphQL 查询自带 `login` / `name` / `slug`，OAuth token 常见 scopes 缺 `read:org` 就整条失败。走 REST `PATCH /repos/<owner>/<repo>/pulls/<n>`，判据是回读一次确认 `title` 与 `body` 首行。

## 收尾要两份签核

适用于一切改动——本机同步、判据改动、清理都算，不是只对 PR。各写一份 `signoff.md`：对象、基准 commit、核过的文件与 md5、跑过的判据与 rc、坏样本、结论。两份都要覆盖全部安装位置。判据：每份里必须出现 `md5`、`rc=`、至少一条坏样本，缺一样按未签计。

**对象一变就重签**：改了任何一处内容，旧签核立即失效，双方按新版重出。签核里写的 md5 与盘上对不上，那份就是废纸。**但重签不等于全清单重签**：只签本次 diff 碰到的项，未变的项写一行「未变，见 <上一份> 的 md5」。判据：本份的项集覆盖本次 diff 涉及的位置；其余项引用得到上一份就算生效。

## 三种失效形状，都真实发生过

- 核的人只回「认可」、没跑判据，下一轮就发现它没读原文。
- 改的人给的判据是恒绿的，例如用 grep 数 `event: error`，而真实帧是 `data: {"type":"error"}`。核的人必须自己造一份坏样本，确认这条判据会红。
- 双方同时改同一个文件，提交进去的是半成品。2026-11-16 实测：同一段两人各写一版，最后三段重复、花了三笔提交合并。预防办法见「动手前看，交回执时写」。

**等对方干活时**：单次 sleep 超过 40 秒容易被工具自己的超时掐断。用 15 到 20 秒一轮，每轮只查一个事实（文件出来了没有、md5 变了没有），别在等待里跑重活。
