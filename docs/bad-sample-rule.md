# 坏样本合格规则

判据能红不等于它在守它声称守的那件事。两条判定，缺一条都算未验证。

## 一、按形态分两格

| 形态 | 做法 | 理由 |
| --- | --- | --- |
| **输入型**（`f(input)` 变异） | 不额外要求 | 坏输入与期望本来就在判据里，多一条断言即可 |
| **变更型**（改源码再跑） | 下面那 4 行差分 | 只测行为，不测声明；没有 helper，也就没有「helper 自己要判据」那层 |

## 二、变更型的模板

```bash
before=$(node probe.mjs)                 # 修复后，被测输出取一次
<改坏源码>
after=$(node probe.mjs)                  # 坏样本下，再取一次
[ "$before" != "$after" ] || { echo "无效坏样本：行为没变，这不是判据的绿"; exit 9; }
node --test <判据文件> > log 2>&1; rc=$?
[ "$rc" -eq 1 ] || { echo "坏样本没让判据红"; exit 9; }
grep -q "<声称要守的断言名>" log || { echo "红了，但不是红在该守的那一条"; exit 9; }
```

为什么需要前 4 行：2026-11-27 造过一次假坏样本 —— 把两行语句换序，行为完全没变，判据 rc=0。
当时差点报「判据恒绿」，实际是**坏样本对被测行为沉默**。它比「判据对某个名字沉默」更危险：
连「我改坏了」都读不出来。

## 三、红的断言名必须对得上

每个坏样本在注释里写一行：`期望红在 <断言名>`。跑完 grep 那一行。

事故（同一天两次）：`rc=1` 就报「能红」，没看红在哪一条。
一次是 `fakeCtx` 缺字段让 ①② 全红而不是 ⑧；一次是 hive 判据红在别的分支。
**红了不等于红在够守的那一条。**

## 四、不做的事

- 不做 `assertBadSample({...})` helper：helper 自己要判据守着，又一层。
- 不写「四字段声明」（名称/改什么/期望断言/两个值）：那是把坏样本当数据写，成本落在每日工作流上；
  变更型的坏样本本来就在现场，两行 shell 拿到的差分比声明更直接。
