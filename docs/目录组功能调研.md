# 目录组（Project Group）功能调研

> 目标：多个工作项目合成一个父项目/父分组，下面挂多个目录。要求**改动最小、影响最小**，
> 且不能破坏 pi 的项目级机制（`.pi/` 配置、AGENTS.md、prompts、mcp、skills、session 分组、trust）。
> 本文为调研结论与最小改动方案，不包含实现代码。

---

## 1. 结论先行

**推荐方案：目录组 = PiDeck 自有状态里的「纯逻辑容器」，成员保持独立项目身份。**

- 组的本质是一层**侧栏分组 + 持久化元数据**，不是真实目录、不是 pi 的 cwd。
- 每个成员仍是独立 Project，继续用自己的目录作为 pi/DSH 的 cwd，所有项目级机制
  （`.pi/prompts`、`.pi/mcp.json`、`.pi/extensions`、`.pi/settings.json`、trust、sessionDir、
  AGENTS.md 发现、git、终端、文件抽屉）**一行都不用改**。
- 代码上完全复刻现有 worktree 父子项目的成熟模式（`worktreeParentId` 先例），
  新增字段全部可选、向后兼容旧 `projects.json`。

一句话：**组是壳，成员是根。pi 不认识组，也不需要认识。**

---

## 2. 现状：PiDeck 的「项目」= 一个目录 = pi 的 cwd

PiDeck 的项目模型是扁平的：`Project`（`src/shared/types/project.ts`）有一条 `path`，
主进程所有 pi 相关能力都以这条 path（= pi 进程 cwd）为锚点：

| 能力 | 锚定方式 | 证据 |
|---|---|---|
| pi 进程启动 | 每个 agent 绑定独立 cwd | `src/main/pi/AgentManager.ts:1473`（`cwd: project.path`）、`AgentManager.ts:673` 注释「每个 agent 绑定独立 cwd，确保 pi 自己发现项目级 AGENTS.md、settings 和 session 分组」 |
| 项目级扩展 | `<cwd>/.pi/extensions` | `src/main/pi/PiProcess.ts:254`、`extensions/enabledExtensionResolver.ts:20,91` |
| 项目级 prompts | `<cwd>/.pi/prompts` | `src/main/prompts/PromptManager.ts:103-129`、`promptWhitelistResolver.ts:30,50` |
| 项目级 mcp | `<cwd>/.pi/mcp.json` | `src/main/config/mcpConfig.ts:62` |
| 项目级 skills | `<cwd>/.pi/agent/skills`、`<cwd>/.agents/skills` | `src/main/resourceDiscovery.ts:83` |
| 会话存储 | 默认 `~/.pi/agent/sessions/<encoded-cwd>/`；自定义 `<cwd>/.pi/sessions` | `src/main/sessions/SessionScanner.ts:1955-1971,2012-2024` |
| 项目信任 | 按 cwd 记录 trustedDirectories | `src/main/config/ConfigManager.ts:291-301`、`AgentManager.ts:4816` |
| 项目资源管理 | `.pi/.agents` 目录 | `src/main/projects/ProjectResourceManager.ts:61-73` |
| DSH 后端 | host 会话 workspace = cwd，会话文件按 cwd 落盘 | `src/main/dsh/DshAgentManager.ts:232,277`、`dshWorkspaceRegistry.ts:104`、`dshSessionPath.ts:11-33` |
| git 面板 / 终端 / 文件抽屉 / 反馈上下文 | 全部 `project.path` / `projectId` | `gitIpc.ts`、`terminal.ts:47`、`filesIpc.ts`、`projectsIpc.ts:253-295` |

**推论（硬约束）**：任何让「成员目录不再作为独立 cwd」的改动（例如 pi 以组目录为 cwd 启动、
或组目录吸收成员的 `.pi`/AGENTS.md），都会让上述全部机制静默切换到错误根目录——会话跑错桶、
项目级配置失效、trust 错位。这正是用户提醒的「pi 有项目级的一些东西，注意影响」。

## 3. 外部工具怎么做（调研）

> 说明：本次外部调研的 web_search 工具在当前环境不可用（无 API key），以下 VS Code 与
> Claude Code 条目来自**官方文档直接抓取**（可引用、已验证）；其余条目基于既有知识，
> 置信度单独标注。web_search 恢复后可补充验证。

### 3.1 VS Code 多根工作区（已验证，官方文档）

- 官方定义：*workspace 是开在一个窗口里的一或多个文件夹的集合*；多根用 `<name>.code-workspace`
  JSON 文件，`folders: [{path}, ...]`。
- 关键事实：**workspace 是配置层容器，不是新目录**。folder 可以来自磁盘上任意位置
  （"work with multiple projects that may not be stored inside the same parent folder"）；
  workspace 级 settings 覆盖用户级、**folder 级 settings 再覆盖 workspace 级**；UI 状态
  （打开的文件、布局）按 workspace 记忆。
- 分层归属：核心编辑器层的 workspace API + `.code-workspace` 文件；每个 folder 仍是独立项目根。
- 启示：业界主流 = 「逻辑容器叠在独立根之上」，容器承载聚合层（设置/UI 状态），
  根保持独立。与方案 A 同构。

来源：https://code.visualstudio.com/docs/editing/workspaces/workspaces

### 3.2 Claude Code（已验证，官方文档）

- **当前官方文档没有独立的「workspace/项目组」容器概念**（llms.txt 索引 192 页无此页）。
  它是严格的单 cwd 模型：`CLAUDE.md` 从 cwd 及其祖先目录加载，`~/.claude/projects/<repo>/memory/`
  按 git 仓库共享自动记忆。
- 多目录支持是 **`--add-dir`**：给会话附加 cwd 之外的目录访问权；配合环境变量
  `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 才会把附加目录的 CLAUDE.md/rules 载入上下文。
  注意默认**不加载**附加目录的记忆——Agent 运行时对「多个根」非常克制。
- 隔离并行用 git worktree（`--worktree`），与 PiDeck 的 worktree 功能同思路。
- 启示：连 Claude Code 都没有把「多目录」做成默认共享层；共享（CLAUDE.md 合并）需要显式
  开关且默认关。这支持方案 A「组 = 纯容器，共享上下文默认不做」的保守取向。

来源：https://code.claude.com/docs/en/memory 、https://code.claude.com/docs/llms.txt

### 3.3 其他工具（基于既有知识，置信度中）

- **JetBrains IntelliJ 系（Project Groups）**：最近项目列表里把多个项目归组。是**纯 UI 分组**，
  不影响项目数据与 IDE 加载——最左端的「纯容器」代表。（置信度：中，未抓官方文档）
- **Cursor**：与 VS Code 兼容，多根工作区沿用 `.code-workspace`；Cursor 1.0 的
  「Workspaces」是协作/分享层面的概念，不是目录分组。（置信度：中）
- **Zed**：支持多根 workspace，roots 相互独立，各自解析配置。（置信度：中）
- **Windsurf / Cline / Roo Code**：项目都是独立目录，规则/记忆文件（`.windsurf/rules`、
  `CLAUDE.md` 等）按目录解析，**没有内置目录组**。（置信度：中）

### 3.4 调研小结

| 工具 | 分组是纯 UI/逻辑容器？ | 是否有成员之上的共享配置层 | 共享层由谁解析 |
|---|---|---|---|
| IntelliJ | ✅ 纯 UI | ❌ | — |
| VS Code | ✅ 配置层容器 | ✅（workspace settings/tasks） | 编辑器核心 |
| Claude Code | ❌（无分组） | ⚠️ 仅 `--add-dir` + 环境变量显式开启 | Agent 运行时 |
| Cursor/Zed | ✅ | ⚠️ 部分 | 编辑器核心 |
| Windsurf/Cline | ❌ | ❌ | — |

**对 PiDeck 的启示**：大多数工具把「组」放在 UI/状态层或编辑器配置层，成员根保持独立；
共享聚合层要么需要运行时支持（VS Code workspace 设置、Claude Code add-dir），要么根本不做
（IntelliJ）。PiDeck 的最小改动路径应落在**最左端**：纯逻辑容器，零共享层。

## 4. 候选方案对比

### 方案 A（推荐）：组 = 纯逻辑容器

- 新增 `Group` 元数据（id/name/成员有序 id 列表），`Project` 加可选 `groupId`。
- 组不出现在 pi 任何链路中；成员仍是独立 Project。
- **影响面**：仅 PiDeck 自有状态层 + 侧栏 UI + i18n。pi/DSH 启动、trust、prompts、mcp、
  extensions、skills、session 扫描、git、终端、文件抽屉 **零改动**。
- **风险**：全部落在侧栏聚合逻辑（搜索/待确认 badge），有 worktree 先例可抄，风险低。

### 方案 B（不推荐）：组 = 真实目录/真实 cwd

- pi 以组目录为 cwd 启动、组目录吸收成员全部项目级配置。
- **爆炸半径**：第 2 节表格里每一行都要跟着改；成员 `.pi/`、AGENTS.md 失效；会话全部
  落到组目录的 session 桶，成员归属丢失；trust 按组目录重新弹；worktree/DSH workspace 全部错位。
  等于把「一个目录 = 一个项目」的产品模型推翻重来。**不满足最小改动，禁止作为默认路径。**

### 方案 C（可选 Phase 2）：组级共享上下文（Claude Code workspace 式）

- 未来若用户想要「组级共享 AGENTS.md / prompts / mcp」，可做显式 opt-in 的覆盖层：
  在 `createPiProcess` 的 prompts/mcp 解析器（`AgentManager.ts:572-585`）里为组内成员
  追加组根目录的解析源。这属于 **pi 行为变更**（组内成员会看到新的 prompts/mcp），
  需要专门测试与开关。**不在本次最小改动范围内**，先留扩展点。

### 边界规则（建议写进实现）

1. **组绝不是 Project 记录**：`AgentManager.getProject()`、`ProjectResourceManager`、
   `projectPresence` 等大量代码假设 `project.path` 存在；worktree 子项目因为有真实 path 才能
   混在 Project 列表里，组没有 path，**必须独立类型/独立存储**。这是本方案最重要的设计约束。
2. 组只收纳**顶级项目**：worktree 子项目（`worktreeParentId` 非空）不可直接入组（其 name 承载
   git 分支名、生命周期跟随父项目）；但**组成员自身可以是 worktree 项目**，其分支在其行内展开。
3. 内置 Chat / 外部会话兑底项目不可入组。
4. 删除组 = 仅解散（清成员 `groupId`），**不删除任何项目与数据**；需确认弹窗。
5. 一个项目最多属于一个组。
6. `groups.json` 缺省为空、`groupId` 缺省为无组：旧数据零迁移。
7. 若项目删除/被移除，`ProjectStore.remove()` 必须同步从组里摘除该成员（防止孤儿引用）。

### 验证建议

- `npm run typecheck`；
- 针对性单测 `node --test tests/<新增组测试>`（ProjectStore 组逻辑可纯函数化）；
- 手工回归：组内成员新建会话 → pi 以成员 cwd 启动（`projects:list-models`、trust 弹窗、
  侧栏会话归属不漂移）；组 + worktree 组合的搜索与待确认 badge 聚合。

## 6. 影响面总结

- **改动面**：`shared` 类型/IPC + `main/projects` + 侧栏 UI + i18n + 测试，约 13 处文件，均为新增。
- **影响面**：pi/DSH 运行时零感知；`.pi/` 全链路（prompts/mcp/extensions/skills/settings/trust/
  sessionDir）零感知；会话扫描与 catalog 零感知；git/终端/文件抽屉零感知。
- **高风险点**：无——方案 A 的设计目标就是把所有风险压缩进「侧栏聚合逻辑」这一个域，
  且该域已有 worktree 的成熟实现可复刻。

## 7. 后续可选项（不在本期）

- 组级共享上下文（方案 C）：需 pi 行为变更，单独评审。
- 拖拽项目进组（本期用菜单/子菜单即可达成，拖拽交互可后置）。
- 组内「一键给所有成员开新会话」（纯 UI 便利，成本低，按需做）。
