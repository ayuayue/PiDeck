# 远端文本编辑与长会话维护方案

> 状态：**阶段一与阶段二均已实施（本工作区，未提交）**。
> 完成目标：多 MiB 项目文本可高效保存；长会话的编辑、删除、重发不再受 256 KiB 整文件往返限制。

## 0. 实施进度

- **项目文本读取/保存：已落地。** 正文改为 SFTP spool 传输；保存是 helper 按读取时 revision 的
  compare-and-swap（`policy: "replace"`，不符即 `FILE_UPLOAD_SOURCE_CHANGED`，一个字节不改）；
  读取是「一次 revision 快照 + 一次 SFTP 下载 + 本地摘要比对」。3 KiB 分块上传与 96 KiB 分块
  回读的旧通道及其常量已删除。
- **限额**：交互式文本编辑 8 MiB（UTF-8 字节，主进程/IPC/草稿三处同源），草稿合计预算 32 MiB
  （超预算拒绝此次输入，不驱逐脏草稿）。冲突、提交回执丢失分别给 `REMOTE_FILE_CHANGED` 与
  `REMOTE_FILE_COMMIT_UNCONFIRMED`，后者文案明确“重新加载核对、不自动重试”。
- **helper 协议**：版本 1.36.2 → 1.37.0，新增稳定码 `FILE_UPLOAD_SOURCE_CHANGED`；artifact 摘要
  pin 与三个版本/摘要夹具同步。顺带修了 artifact 内 `close()` 名重屏蔽（会把描述符关闭变成
  “扫掉全部待提交 stage”）的潜伏缺陷。
- **验证**：定向 173 项通过；`tsc` 错误集与改动前基线逐条相同（12 条均来自 5 个未安装依赖）。
- **未验证**：真实 SSH + Electron 链路（需要授权主机），包括吞吐、命令数、峰值内存，以及
  `readBase64` 大文件预览的实际耗时。不要拿单元测试代替这一项。
- **阶段二：已落地。** 新增冻结 artifact `session-maintain.mjs`（摘要 pin 化）与宿主级方法
  `session.maintain`，helper 1.38.0；`RemoteSessionHistoryWriter` 从 913 行降到 322 行，只做
  「解析路径 → 取 revision 快照 → 一次请求 → 映射结果」，整文件下载/分块上传与 256 KiB 上界
  连实现一起删除。远端流式两遍扫描（索引 + 逐行复制）保内存与文件体积无关，未改动的行逐字节保留。
- **失败语义**：请求帧未发出的连接码原样透出；对端亲自回答的稳定码原样映射；其余（超时/断连/
  无码抛出）一律“结果未确认”，不重放。重发草稿超限时历史**不改**，报新的会话命令码
  `SESSION_DRAFT_TOO_LARGE`（三处映射 + 中英繁文案）。
- **快照上界同步**：`REMOTE_SESSION_WRITE_MAX_BYTES` 从旧的 256 KiB 改为与会话维护文件上界同源
  （512 MiB），否则先把上界放飞、又在取 revision 时按 256 KiB 拒掉，大会话仍会在第一 步失败。
  代价是每次维护在远端多算一次 O(文件) 摘要（不再付整文传输），已用「300 KiB 会话可快照」用例钉住。
- **阶段二验证**：定向 234 项通过（含与本地编辑器逐字节对齐的 parity、mutation UI、协调器夹具）；
  阶段一 107 项回归通过；`tsc` 错误集仍与基线逐条相同。
- **阶段二尚存缺口**（已知、未掩盖）：①维护与「会话重新激活」之间仍只是前后两次检查，没有全程
  互斥锁——与旧实现同风险，真正上锁要改激活/发送入口，留作独立任务；②远端历史**分页显示**仍只在
  当前字节窗口内应用 context_edit 与分支判定，跨页一致性要等把索引查询也搬到远端；③真实 SSH 未验。

## 1. 推荐决策

**项目文件复用现有 SFTP 流式传输，由 helper 做带版本检查的提交；会话历史在远端就地流式处理，本机只传操作及必要正文。**

沿用系统 OpenSSH、现有 helper 控制连接、既有 SFTP 执行器与 pi JSONL 格式。新增的会话维护能力是受限文件操作，不调用模型、不接管 Agent，不新增 pi RPC 通道、常驻 server 或会话数据库。

这两个领域共享传输和任务生命周期基础，但保留各自的授权、定位和提交规则。项目路径权限不能自动变成会话目录权限。

## 2. 已核实的基础与缺口

| 当前实现 | 对方案的影响 |
|---|---|
| `RemoteProjectFileService` 保存按 3 KiB 发 SSH 短命令；1 MiB 正文需要 342 条上传命令，另有快照与提交 | 放大容量前先替换传输路径 |
| `RemoteProjectFileCommands` 的每次分块读取都会整文件读取、算摘要后切片 | 新读路径应只顺序传输一次正文，单独核对版本与摘要 |
| `RemoteProjectUploadJob` 已有 SFTP stage、进度、取消、摘要校验和 helper 提交 | 复用现成基础，不再引入 SSH/SFTP 客户端 |
| `RemoteUploadCommitSource` 当前只允许 `policy: create`，拒绝覆盖已有文件 | 文本保存需要新增明确的条件替换分支，不能直接调用现有上传冒充保存 |
| `RemoteSessionHistoryWriter` 把整个 JSONL 下载到本机、修改后以 4 KiB 命令分块上传 | 256 KiB 是这条维护路径的成本限制；正常对话不经过它 |
| 本地 `SessionFileEditor` 已有流式扫描、按行复制及改写计划 | 复用必要的 JSONL 语义与流式基础，消除远端重复实现 |
| 现有会话编辑/删除产生 `context_edit`，重发产生 `deleted` 墓碑 | 改传输与执行位置，保留活动分支、过程链和历史格式语义 |
| 协调器在维护前后检查停止状态，但维护与激活之间没有完整的操作互斥 | 本次需在维护全程阻止同一会话重新激活 |
| `RemoteSessionHistoryReader` 当前只在读取窗口内应用分支与 `context_edit` 投影 | 长会话编辑可能跨页；分页回读必须拿到当前全局分支和编辑事实 |

## 3. 项目文本：SFTP 暂存 + 条件替换

### 读取

1. 主进程从已登记 project/root 解析目标，helper 返回身份与内容摘要；超过编辑预算时在传输正文前拒绝。
2. 用现有 SFTP download 流式写入本机私密临时文件，校验实际字节数、摘要和连接代。完成后复核远端版本；有变化就拒绝这次快照。
3. 在编辑预算内严格解码 UTF-8，保留 BOM 和换行规则；沿用主进程签发的不透明 version。临时文件完成或失败后清理。

### 保存

1. 沿用 `projectId + relativePath + version + content` 的应用入口。主进程校验版本归属与 UTF-8 字节数，生成私密暂存文件和内容摘要。
2. 扩展现有 prepare/commit 事务，新增显式的 `replace-if-version` 策略，绑定旧文件 revision、项目根、连接代、目标与新内容摘要；原有 create-only 上传语义保持独立。
3. 复用 SFTP stage 将正文送入受控 spool。正文不放进 SSH argv；8 KiB 命令长度门禁保持原值。
4. helper 在目标目录创建排他临时文件，流式校验并复制暂存内容；提交前再次检查旧 revision，保留原权限和现有 uid/gid 要求，fsync 后同目录 rename，并按平台能力同步目录。
5. 收到并核实回执后推进 version，触发现有文件树/Git 事实失效。冲突与失败保留编辑草稿；不能把发送时的正文覆盖用户后来继续输入的内容。

路径检查沿用 fd 锚定与非链接校验。prepare 的成功不替代 commit 时的检查。只由 helper 发布目标，SFTP 不直接覆盖用户文件。

### 容量与交互

- **交互式文本编辑首版目标：8 MiB（按 UTF-8 字节）。** 主进程、IPC、草稿输入预算和文案保持一致。多字节文本不能直到保存时才发现超限。
- 草稿保留现有最多 5 个文件，同时增加总正文预算，初始目标 32 MiB，计入编辑正文与保存基线；脏草稿不得静默驱逐。保存中的快照和编辑器自身开销另做峰值内存验收，32 MiB 不代表整个 renderer 的内存占用。
- 超过 8 MiB 提供下载入口，不把截断预览当成可保存全文。普通上传/下载沿用自己的现有容量政策，不受文本编辑上限约束。
- 8 MiB 是否可上线由真实编辑器打开、长行、输入、撤销、保存与多草稿测试决定。传输先迁移并验证，再提高编辑上限。

## 4. 会话历史：在远端执行受限维护任务

### 执行与授权

主进程只提交会话身份、目标 entryId、操作类型、预期版本及必要的新正文。沿用 helper 控制连接调度固定的短生命周期 Node worker，stdout 只返回有界进度与结果；不让主 helper 同步扫描大文件而阻塞目录、Git 等请求。

worker 的写动作只支持 edit/delete/resend；读动作仅服务已登记会话的分页、草稿与结果核实。会话位置由主进程已登记 locator 和远端允许的会话根共同验证，覆盖默认根与已支持的项目 `sessionDir`。renderer 不提交任意绝对路径或代码；不能把项目 helper 的普通 `fs.*` 根边界放宽到用户 home。

先在 `host-boundaries.md` 与 helper 契约中说明此固定文件域，再实现版本化部署与 capability 协商。旧 helper 不支持时明确提示更新能力，不在失败后自动切回旧写路径。

### JSONL 处理

1. 只允许已停止的会话进入维护；协调器的同一会话操作锁覆盖维护与激活/发送入口。远端按物理会话文件串行维护，避免不同窗口或 helper 实例互相覆盖。
2. 流式扫描 JSONL，建立条目 id、父链、角色、字节偏移等轻量索引，校验活动分支与目标身份。只在需要时读取目标正文。
3. edit/delete 继续生成 pi 原生 `context_edit`；resend 继续按既有规则处理目标及后继墓碑。复用本地纯语义，保留本地/远端一致性测试。
4. 首版统一流式生成同目录临时文件：未变化行原样复制，新增编辑记录放到尾部。保留现有原子发布保障，不直接向原文件追加可能写到一半的记录。
5. 提交前校验源 revision/摘要，验证临时文件完整性与权限后原子替换，保留受控备份及可核查的操作身份。成功后刷新现有历史页，下次用户发送时再由 pi 加载。

远端磁盘工作仍约为 O(历史大小)，但网络正文传输量变成 O(此次编辑内容或所需重发草稿)，不会随完整历史一起增长。

复用本地流式代码需要两处限定：只提取维护所需的纯逻辑/IO，不把 Electron logger、运行时 reload 等宿主依赖部署过去；索引不累计所有 `context_edit` 的替换正文，按偏移读取需要的记录。现有流式实现的索引仍随条目数增长，不能宣称恒定内存。

### 分页显示

长会话的保存与回读作为一个交付单元：位于文件末尾的 `context_edit` 也必须作用于较早页面的目标消息。沿用有界分页接口，由远端依据完整的轻量索引确定当前活动分支、压缩边界和有效编辑，再返回该页实际正文；不能只在当前字节窗口内解释记录。游标/缓存绑定文件 revision，维护后失效并重新取页，防止拼接新旧状态。本轮按需构建索引，限制条目数，不增加持久化索引数据库。

### 重发与资源预算

- 重发涉及的文本/图片可能很大。先以有界分块完整取回并缓存重发草稿，再提交历史变更；不能先裁剪历史再发现草稿回包超过协议限制。附件预算与历史总大小分开处理。
- 取消只在提交前保证原文件不变。提交附近断线或取消后先核实结果，禁止自动再次改写或自动发送重发消息。
- 去掉 256 KiB 整文件传输成本限制。首版验收至少覆盖 **100 MiB 历史文件**，这是一项验收规模，不是正常对话的容量上限。
- 维护资源采用独立预算，初始候选值：IO 块 256 KiB、单行 32 MiB、条目索引 20 万条、单任务 120 秒、每主机最多 2 个维护 worker。同一会话始终只允许一个维护任务。
- 单行预算必须在累积完整行之前生效；索引、改写计划和草稿回传也需限额。超预算返回对应的维护限制并保持原文件，不能截断保存。候选预算经压力测试后冻结。

## 5. 失败语义与实际保证

| 结果 | 应用行为 |
|---|---|
| 提交前取消、权限错误、内容校验失败 | 不改变目标；保留草稿；清理本操作持有的临时资源 |
| 版本冲突 | 不覆盖，提示重新读取；保留用户编辑 |
| 已核实提交成功 | 推进版本并刷新相关事实 |
| 提交已发送但回执丢失 | 显示结果待核实；按操作身份、版本与摘要查询，不自动重放 |
| 连接换代、项目重绑、窗口销毁 | 旧任务结果不得写入新状态；只清理该任务拥有的资源 |

锁能串行化 PiDeck 管理的写入与启动；外部 CLI/编辑器绕过这些锁时，提交前版本检查仍属于乐观冲突检测，检查到 rename 之间不是文件系统原生 CAS。方案不承诺阻止任意外部并发写，也不引入强制终止外部进程的行为。

## 6. 实施顺序与交付单元

1. **文本传输迁移。** 完成条件替换契约、SFTP 接线、版本/失败语义与针对性验证。先保持 1 MiB 行为，验证通过后删除对应 3 KiB 上传命令循环及重复整读路径，再连同草稿预算提高到 8 MiB。
2. **远端会话维护。** 用现有一致性夹具约束纯语义提取；接入受限 worker、会话操作互斥和有界草稿回传。100 MiB 用例与故障用例通过后删除旧整文件下载/上传改写链，移除其 256 KiB 成本门槛。清理仅限失去调用者的代码，不删除其他领域仍使用的边界工具。
3. **真实 SSH + Electron 验收。** 在明确授权的测试主机/目录验证两条完整链路，记录实际耗时、SSH 进程/命令数、传输字节、主进程/worker/renderer 峰值内存。只读源码和模拟测试不能替代这一项。

每个单元可独立回滚代码；JSONL 格式不迁移，不需要改写存量会话。写操作的不确定结果只能核实，不能借回滚自动重放。当前工作区的并行修改按文件归属协调，本提案不覆盖它们。

## 7. 验收标准

- 文本：空文件、中文/BOM/CRLF、1/4/8 MiB、上限加 1 字节、长单行；原文可无损往返，超限输入不丢已有草稿。
- 文本传输：文件体积从 1 到 8 MiB 时，SSH 会话/控制命令数保持固定级别，不按 3 KiB 增长；吞吐和内存实测后报告，不预先承诺加速倍数。
- 会话：超过 256 KiB 的回归样本，以及 1/20/100 MiB 文件的编辑、删除、重发；处理分支、工具过程链、既有 context_edit、墓碑、图片和损坏 JSONL。
- 会话结果：与本地编辑器在同一夹具上的有效上下文和墓碑语义一致，未变更行保持字节一致；验证编辑文件开头的消息后，尾页、向前翻页、重新打开和后续 pi 恢复均一致，跨页 context_edit、分支和压缩边界不能漏掉。
- 大会话网络量：编辑固定大小文本时，从 1 到 100 MiB 增大历史不应增加整份历史上传/下载；重发只回传目标草稿需要的内容。
- 故障：传输中断、磁盘满、提交前取消、提交后丢回执、源文件并发变化、路径替换、过期版本、重复提交、重连和跨项目隔离；不损坏文件、不误报成功、不丢草稿。
- 并发：维护期间激活/发送受互斥保护；维护 A 不阻塞 B 的普通控制请求；索引/单行/超时预算都在发生无界分配前生效。
- 执行 `npm run typecheck`、受影响的针对性测试和相关 E2E；原生代码若有改动只测试/构建 `native/remote-sftp`，不做全仓构建。

## 8. 对 ZCode 的借鉴边界

ZCode 的会话存储、历史分页和文件分块分别设限，说明累计历史与一次传输可以独立管理。PiDeck 应借鉴这个分工，同时尊重 pi 的 JSONL 所有权与现有宿主边界。ZCode 的 SQLite 存储和 SSH 部署上传不直接替代 PiDeck 的历史语义及带版本的文件保存。
