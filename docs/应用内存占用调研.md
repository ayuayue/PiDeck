## 1. 结论摘要

**用户假设核实**：用户提出「Agent 走 RPC 跑在 PiDeck 进程外，为什么 PiDeck 内存还这么大」——
**假设成立**，实测 pi agent 是独立 `node.exe`（368 MB，单独计账），PiDeck 的 ~1 GB 全部是它自己的。

**根因（按贡献量级排序）**：

| # | 根因 | 性质 | 证据强度 |
|---|---|---|---|
| A | 渲染进程 V8 老生代上限 **2048 MB**，而正常会话 JS 峰值仅 **~185 MB**（11× 余量）→ V8 无收缩压力，committed 堆只涨不还，RSS 停在高水位 | 结构性 | 实测 + 代码注释 |
| B | 渲染进程 **Chromium 原生内存**（布局/栅格化）——DOM 节点数被限得很紧，但**单轮内容体积无上界** | 结构性 | 仓库自述事故注释 |
| C | Chromium **多进程底噪**：空白窗口即 321 MB（5 个进程各一份 V8/Blink/共享库） | 架构固有 | 对照组实测 |
| D | 会话消息缓存对「**打开着的 Tab 全部保留**」，且淘汰只在写入路径触发 | 策略选择 | 代码证据 |
| E | runtime 会话**向上翻历史的前缀合并没有上界**（同文件 disk 路径有 2400 上限） | 实现缺口 | 代码对照 |
| F | 附件栏 base64 无 TTL；生图「重发带回参考图」主动把 ref 水合成 base64 | 实现缺口 | 代码证据 |
| G | 音频服务常驻 **50~85 MB**，而代码编辑器无任何音频需求 | 缺配置 | 进程实测 |
| H | GPU 进程 91~254 MB（空白 Electron 仅 97.8 MB）；`zoomFactor=1.05` 非整数缩放放大栅格化 | 叠加 | 进程实测 + 代码 |

**关键否证**：主进程 98~158 MB **不是泄漏**（V8 `heapUsed` 仅 14 MB）——是 Electron/Node/native 基线与 committed 堆，
且现有仪表工具本身**采不到**这部分（见 §4）。

## 2. 观测口径：PiDeck 是 5 个进程，不是 1 个

任务管理器里「PiDeck」为一组进程，合并口径才是真实占用。你的实例进程树（实测）：

```
Main (Browser)          ← PiDeck.exe
├── gpu-process         ← 合成/栅格化
├── renderer            ← UI（本文的 A/B/D/E/F/H 都发生在这里）
├── utility --utility-sub-type=network.mojom.NetworkService
├── utility --utility-sub-type=audio.mojom.AudioService   ← G：编辑器的纯浪费
└── utility --utility-sub-type=node.mojom.NodeService      ← dev 实例里的 DSH host
```

**空白窗口对照实验**（同一 Electron 版本、不加载任何页面，仅 `no-sandbox`）：

| 进程 | 空白 Electron | 正式版空载（无会话） | 你的实例（运行 14 h） |
|---|---|---|---|
| Main | 105.6 | 158 | 98～141 |
| gpu-process | 97.8 | 172 | 91～157 |
| renderer | 65.0 | 211 | **557～807** |
| utility network | 52.9 | 68 | 27 |
| utility audio | — | — | 53～85 |
| **合计** | **321 MB** | **~610 MB** | **~950 MB～1.0 GB** |

三个可读结论：

1. **空白 Electron 就要 321 MB** ——这是 Chromium 多进程架构的底噪，与 PiDeck 代码质量无关。
   因此「别人加了 Agent 也没这么大」的对比前提不成立：别人小是因为没有 PiDeck 这层前端。
2. **PiDeck 自身叠加约 290 MB**（610 − 321），来自前端 bundle（见 §6.7）与更宽的窗口/更多合成层。
3. **只有 renderer 是「会随时间长大」的进程**（65 → 211 → 557~807 MB），其余进程基本平（见 §5）。

## 3. Agent 隔离性核实（实测，非推理）

| 进程 | 父进程 | 内存 |
|---|---|---|
| pi agent（全局 `pi-coding-agent` 的 `node.exe`） | PiDeck Main | **368 MB** |
| 本次调研派生的 2 个 subagent | 各自独立 `node` | 各 ~375 MB |

**结论**：RPC 架构正确履行了职责——Agent 内存完全独立计账，不进 PiDeck。
用户「Agent 不在 PiDeck 进程里」的判断正确；cron 结论是「PiDeck 的问题与 Agent 无关」。

## 4. 主进程：`heapUsed` 14 MB vs RSS 98~158 MB —— 不是泄漏，是仪表缺列

`src/main/memory/MemoryMonitor.ts:129,133`（`mainProcessRow()`）对主进程**只采两个字段**：

```ts
rssKB: Math.round(m.rss / 1024),
heapUsedKB: Math.round(m.heapUsed / 1024),
```

`heapTotal` / `external` / `arrayBuffers` / native 分配**一个都没采**。
所以「152 MB vs 14 MB」的差值在这套仪表里按设计就不可见——**这是可观测性缺口，不是异常信号**。

真实构成：Electron + Node 运行时基线 + `node-pty` / `node:sqlite` 原生模块映射 + **V8 committed 堆**。

仓库自己在 `src/main/index.ts:95` 注释里记录过该现象：

> V8 没有压力就不主动收缩，会话消息/代码块高亮等大对象把堆撑大后 committed 空间长期不归还 OS
> （内存采样实测：**V8 总 55 MB → 210 MB 不回落，RSS 基线随每次操作抬升**）

这正是主进程 `--max-old-space-size` 被压到 **384 MB** 的原因（`src/main/v8HeapLimits.ts:103`）——
**同一个机制在渲染进程上以更大的尺度重演（§5.1）**。

## 5. 渲染进程：唯一真正「会长大」的进程

### 5.1 根因 A：V8 老生代上限 2048 MB，相对实际峰值有 11× 余量

`src/main/v8HeapLimits.ts:100`：

```ts
export const RENDERER_MAX_OLD_SPACE_MB = 2048;
```

该常量 docstring 自述理由：

> 取 2GB：既远高于正常会话的 JS 峰值（**~185MB**），也高于 Chromium 在 8GB 机器上的默认档位量级……

**本环境实测验证生效**：用 CDP 连入隔离实例，读到 `performance.memory.jsHeapSizeLimit = 2222.1 MB`（2048 MiB + 新生代）。

全篇最关键的一组对照数字：

> **代码作者实测「正常会话 JS 峰值 ≈ 185 MB」，而观测到的 renderer RSS 稳定在 557~807 MB。**

即 **600 MB+ 不在 JS 堆里**（属 §5.2 的 Chromium 原生内存 + V8 committed 未归还）。
机制：上限相对实际用量宽松 → V8 迟迟不做 major GC → committed 空间只涨不还 → RSS 停在高水位。

**现象吻合**：对运行中实例连续采样，renderer 呈 **807 → 578 → 557 → 616 → 800 MB** 的锯齿。
这种「能掉 250 MB 又涨回来」的形态是「高分配速率 + 高水位不回落」的典型特征，
**而非稳定引用泄漏**（真实泄漏不会自己回落）。

> 补充（避免误读）：在 16 GB 机器上 Chromium 的默认上限本身高达数 GB，所以 2048 并非「异常宽松」；
> 问题在于它相对**本应用实测的 185 MB 峰值**仍宽松一个数量级，因而丧失了「施加回收压力」的作用。

### 5.2 根因 B：Chromium 原生内存（布局 + 栅格化），仓库自己踩过

`src/renderer/src/components/session/MarkdownStream.tsx:38`：

> 大文本（100K+）下主线程被排满 → IPC 消息积压 → **渲染进程原生内存 GB 级爬升**。

`:186` 另有实测记录：

> 重渲染（**大代码块流式输出时 GC 追不上，原生内存实测 200-450 MB/min 爬升**）

缓解手段是 `MarkdownStream.tsx:44` 的 `PLAIN_SPLIT_STEP = 4_096` 分片 + 冻结段缓存。

**DOM 规模本身被限制得很紧**（这也解释了空载实例 DOM 仅 560~632 个节点）：

| 预算 | 值 | 位置 |
|---|---|---|
| 贴底只挂尾部轮数 | 3 | `src/renderer/src/components/session/timeline/turnRenderWindow.ts:12` |
| 上滚 cohort / 扩窗步长 | 3 / 3 | `.../turnRenderWindow.ts:14`（`TIMELINE_SCROLLED_TURN_LIMIT`）、`:16`（`TIMELINE_WINDOW_EXPAND_STEP`） |
| 单轮 step 预算 | 120 | `src/renderer/src/components/session/timeline/turnMountBudget.ts:21`（`TIMELINE_MOUNTED_STEP_LIMIT`） |

**风险不在节点数，在单轮内容体积**——`turnRenderWindow.ts` 注释明确「单轮再大也整轮保留」。

### 5.3 根因 D：会话消息缓存对「打开的 Tab」不设上限

- `src/renderer/src/atoms/session-atoms.ts:19`：`SESSION_MESSAGE_CACHE_LIMIT = 8`
- 但 `selectRetainedCacheEntryIds`（`:32`）对打开的 Tab 一律保活，`:34` 注释原文：

  > 宁可在内存上稍微超额，也绝不挤掉正在显示的会话

- **pinned Tab 落 localStorage 跨重启恢复**：`const PINNED_TABS_STORAGE_KEY = "pideck.pinnedSessionTabIds";`（`src/renderer/src/hooks/useSessionWorkspaceChrome.ts:8`；读取 `:43`、回写 `:98`）
- **淘汰只在写入路径触发**（`session-atoms.ts:606`，位于 `cacheSessionMessagesAtom` 尾部）
  → 用户只切会话、不发送的时段，缓存永不收缩
- **全仓没有任何字节预算常量**（只有条目数 8）。用户的会话 jsonl 普遍 0.8~3.8 MB，
  解析成 `ChatMessage[]` 后通常是文件体积的 1.5~3×。

> 需与既有文档对齐：`长会话内存治理方案.md` §5.1 记录常量为 8 及其历史（曾收为 6，后放宽回 8）。
> 本文补充的是「**打开 Tab 不受此上限约束**」与「**淘汰仅发生在写入路径**」这两个此前未记录的性质。

### 5.4 根因 E：runtime 历史前缀合并缺上界（disk 路径有）

| 路径 | 位置 | 上界 |
|---|---|---|
| disk 翻页 | `session-atoms.ts:626` `DISK_HISTORY_MESSAGE_LIMIT = 2400`，`:652` 处 `splice(0, overflow)` | **有** |
| runtime 上翻 | `session-atoms.ts:794` `const merged = [...freshMessages, ...baseMessages];` | **无** |

**同一文件两条路径不对称**，runtime 路径少了一道闸。单会话前缀可达 10~100 MB 量级。
释放依赖 `clearSessionHistoryAtom`，且其前提是「回底稳定后」（`长会话内存治理方案.md` §5.3 记 1500 ms）——
用户停在会话中途或切走时，前缀持续挂载。

### 5.5 根因 F：附件栏 base64 无 TTL，生图重发还会主动水合成 base64

- `src/renderer/src/atoms/composer-atoms.ts:39`：`sessionAttachmentsByIdAtom: atom<Record<string, ImageContent[]>>({})`
  存 `ImageContent.data`（**base64 字面量**），**无上限、无 TTL**——贴了图不发送即常驻。
- `src/renderer/src/App.tsx:2603`：`hydrateImageContents(images, (ref) => window.piDesktop.imagegen.readImageBlob(ref))`
  ——**主动**把磁盘 `ref` 读回 base64 塞进附件栏（生图「重发带回参考图」路径）。多张参考图 × 多次重试 = 数十~数百 MB。

> 注意这不是 2026-09 白屏事故的复发：事故点是「base64 落进 JSONL」，
> 该纪律（下盘只留 `ref`、读取有字节上界）仍成立。本条说的是**渲染层内存里的临时形态没有回收策略**。

### 5.6 根因 H：GPU 进程偏高

空白 Electron 的 gpu-process 为 97.8 MB；PiDeck 实测 91~254 MB（dev 实例 253.9 MB）。
`backdrop-filter`/`blur` 在 4 个 CSS 文件 + 6 个组件中使用（`styles/{streamdownChrome,timeline,workspace,surfaces}.css`、
`components/motion/{dock,drawer,morphing-search}.tsx`、`components/session/SessionSurfaceStage.tsx` 等）。
另：用户设置 `zoomFactor = 1.05` 属**非整数缩放**，会放大栅格化尺寸并提高重栅格化频率。

### 5.7 叠加因素：首屏即加载的前端体量

渲染层产物共 ~27 MB；首屏主 chunk `index-*.js` **5.5 MB**（未压缩），另有 `vendor-markdown` 1.71 MB。
**streamdown / katex / xterm 为静态 import 常驻**（`MarkdownStream.tsx:1-6` 等）；
shiki 已正确做成懒加载单例（`components/agents/agent-code.tsx:32` `import("shiki")`，注册 5 种语言 2 主题），
语言 grammar 走动态 import 按需拆 chunk——这块**设计正确，不是问题**。

### 5.8 小的：atomFamily 实例缺配对释放

全渲染层 34 处 `atomFamily(` / 仅 14 处 `.remove(`。确证的一处遗漏：
`removeSessionComposerStateAtom`（`src/renderer/src/atoms/composer-atoms.ts:247-269`）依次删除
drafts / attachments / pasteFiles / modes / sendStates / modelPending，
**未清理 `sessionQuotesByIdAtom`** → 「写了引用但没发送」的会话其引用文本常驻到进程重启。
量级 KB~低 MB，不是主因。

### 5.9 已排除的假设（避免后续重复排查）

| 假设 | 实测结论 |
|---|---|
| 会话数据在渲染层无限累积 | **有 LRU 上界**：`sessionMessageLruAtom`（`src/renderer/src/atoms/session-atoms.ts:400`）按 8 会话滚动淘汰，写入处 `:681` `...slice(0, SESSION_MESSAGE_CACHE_LIMIT)`（另见 `长会话内存治理方案.md` §5.1） |
| 打开过的会话永久保留完整消息 | 部分成立但受限：受 8 上限约束，**例外是打开中的 Tab 与 pinned Tab**（§5.3） |
| DOM 全量挂载导致渲染进程膨胀 | **否**：窗口化很紧（3 轮 / 120 step），空载 DOM 仅 560~632 节点 |
| 终端（xterm）常驻 | **否**：关闭即 `terminal.dispose()` 配对（`src/renderer/src/components/terminal/TerminalDock.tsx:324`），仅打开期间有 `scrollback: 5000`（`:280`） |
| webview 留在 DOM 导致 guest 常驻 | **否**：随组件卸载重建（`src/renderer/src/components/app/BrowserPanel.tsx:55` 注释：「真正的 WebContents 仍随组件挂载重建，避免同时运行两个 webview 实例」） |
| 图片 base64 全量驻留 | 历史图走 `pideck-img://blob/<ref>` 自定义协议按需加载；仅「生成中」与「附件栏」为内联 base64（§5.5） |
| 主进程会话扫描/日志/事件缓冲无界 | **否**：`AgentManager` 12 轮 / `SessionHistoryReader` 索引 ≤32 / `LogLineCache` 32×8 MiB（仅开日志页才填）/ processEvents 1200 行·512 KiB 且流式落盘 |
| 工具调用/RPC 流量导致内存增长 | **否**：有行数与字节双上界 |

## 6. 卡顿与内存的关系

渲染进程堆到 800 MB~1 GB 时，**V8 major GC 停顿随堆规模增长** → 数百毫秒级卡顿，且 GC 前持续「虚胖」。
这是根因 A 的直接后果，与 §5.1 的锯齿形态互为印证。

但卡顿还有一条**独立**来源需要单独定量：**事件循环延迟**。
本仓库已内置探针（`src/main/diagnostics/DiagnosticsMonitor.ts`，记录 event-loop lag 及峰值），
但用户当前设置关闭：

```
settings.json → developerDiagnostics: false
```

**建议先开启「设置 → 开发 → 性能诊断」**（`src/renderer/src/components/app/settings/DiagnosticsPanel.tsx`），
跑一两天后看 `diagnostics` 文件夹，即可把「卡顿」拆解为「GC 停顿」还是「主进程事件循环阻塞」——
在拿到这份数据前，不应把卡顿全部归因于内存。

## 7. 复现与验证方法（只读，无需改代码）

### 7.1 内置内存采样（`PIDECK_MEMORY_PROFILE=1`）

```
PIDECK_MEMORY_PROFILE=1 npm run dev                    # 默认 5 s 一次
PIDECK_MEMORY_PROFILE=1 PIDECK_MEMORY_PROFILE_INTERVAL_MS=2000 npm run dev
```

输出 `<userData>/memory-profile/profile-<ts>.csv`，表头含
`rssKB,privateKB,sharedKB,peakRssKB,heapUsedKB,jsHeapTotalKB,domNodes,imgCount,imgPixels,canvasPixels,workerCount,workerJSHeapKB,streaming`
（实现在 `src/main/memory/MemoryMonitor.ts`，编解码在 `src/main/memory/memoryProfileCsv.ts`）。
**这是唯一能同时看到「renderer 的 DOM 节点数 / 图片像素 / canvas 像素 / worker 堆」的途径**。

> 已知缺口：主进程行只采 `rss` + `heapUsed`（§4）。若要解释主进程非 JS 内存，
> 应先补采 `heapTotal` / `external` / `arrayBuffers`（低成本、纯仪表改动）。

### 7.2 隔离实例 + CDP 探查（不污染正式 userData）

```bash
PIDECK_MEMORY_PROFILE=1 npx electron . --user-data-dir="<临时目录>" --remote-debugging-port=<port>
# 另开终端：http://127.0.0.1:<port>/json/list 取 webSocketDebuggerUrl，再 Runtime.evaluate：
#   performance.memory（usedJSHeapSize / totalJSHeapSize / jsHeapSizeLimit）
#   document.querySelectorAll('*').length、document.images、canvas 像素
```

本次调研即用此法验证「空载 renderer 的 JS 堆仅 48 MB、DOM 560~632 节点、0 张图片」，
从而排除「DOM/图片撑起 762 MB」的猜测。

### 7.3 堆快照定位真实引用

对长跑实例（**需先开启 DevTools 可用性**）在 Memory 面板取两次堆快照并 diff，
重点看 `sessionMessagesCacheAtom` 的 key 数与各 entry 的 retained size —— 用于确认 §5.3 是否超配。

### 7.4 进程树核对

```powershell
Get-CimInstance Win32_Process -Filter "Name='PiDeck.exe' OR Name='electron.exe'" |
  Select-Object ProcessId,ParentProcessId,Name,CommandLine
```

注意 `WorkingSet` 含共享页，判断「私有内存」要看 `PrivateMemorySize64`。

## 9. 未验证 / 存疑项

- **762 MB（及观测到的 807 MB）中 JS 堆 vs Chromium 原生内存的确切占比**——空载实例的 48 MB 堆不足以外推；
  需 §7.3 堆快照 + §7.1 原生内存列共同确认。
- **长跑实例 `sessionMessagesCacheAtom` 的实际条目数与字节数**——取决于会话 Tab 是否被长期保留。
- **runtime 历史前缀在真实使用中累计到什么程度**——取决于用户滚动深度。
- **`zoomFactor=1.05` + `expandInterimDuringStream=true` 对合成层内存的贡献比例**——机制合理但无本地数据。
- **`URL.createObjectURL` 是否有 revoke 配对**：`components/app/FileDiffViewer.tsx`、`ConfigModal.tsx`、`ModelsExportPanel.tsx` 各有一处，未逐一核实。
- **`RENDERER_MAX_OLD_SPACE_MB` 降到 1024 是否安全**——受既有限制说明约束，需实测验证后方可判定。
- 关闭浏览器抽屉后 guest 渲染进程是否真正退出（进程树核对）；本文只在代码层确认了「webview 随组件卸载重建」。
